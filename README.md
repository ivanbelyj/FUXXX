# Messenger

HTML-native messenger for humans and machines.

Минималистичный мессенджер «для бунтарей»: ноль зависимостей, ноль аккаунтов,
ноль инфраструктуры. Чистый Node.js на сервере и чистый HTML+JS на клиенте.

- **fuck FRAMEWORKS** — на сервере нет ни одного npm-пакета (только `node:*`).
- **fuck CORPS** — чаты живут на твоём VPS; приглашение = ссылка, аккаунтов нет.
- **fuck DPI** — обычный HTTP + SSE, легко прячется за любым reverse-proxy.
- **fuck RICH** — мессенджер для бедняков: один Node.js, 1 CPU, ноль инфраструктуры.
- **fuck REAL LIFE** — companion-agnostic: человек и ИИ в одном чате, на равных.
- **fuck VOICE MESSAGES** — только текст, фото и видео.

Сами лозунги живут в самом приложении: при каждом заходе на логотип ложится
случайный слоган из набора (мелким повёрнутым текстом оттиском поперёк низа лого — с
жёсткой подложкой цветом фона, без мигания). Отдельного экрана-«манифеста» нет —
принципы проступают по одному.

## Быстрый старт

```bash
node --env-file=.env server/index.js
# или без .env (всё через переменные окружения):
AI_API_KEY=sk-... node server/index.js
```

Открой `http://localhost:8787`, впиши имя, нажми **Создать чат** — получишь
ссылку-приглашение вида `http://host/j/<roomId>`. Кто по ней перейдёт — попадёт в
тот же чат. Перезагрузка сервера и браузера историю не теряет.

`.env.example` — шаблон: скопируй его в `.env` и замени заглушки вида `__AI_API_KEY__`
своими значениями (сервер читает переменные окружения; удобно запускать через
`node --env-file=.env` или через systemd). Тот же файл — источник `.env` для прода: CI
рендерит из него `/opt/messenger/.env` по секретам GitHub (см. «Деплой»), поэтому на VPS
`.env` руками не заводят.

## Архитектура (на пальцах)

```
браузер ──POST /api/rooms/:id/messages──▶ Node http ──append──▶ data/rooms/<id>.jsonl
   ▲                                          │
   └────────── SSE /api/rooms/:id/events ─────┘  (рассылка всем в комнате)
                                              │
                              POST /api/rooms/:id/ai ─▶ OpenAI-совместимый API
                                                        (ключ только на сервере)
```

- **Реалтайм** — Server-Sent Events. Это обычный HTTP: работает через любые прокси,
  не требует WebSocket-библиотек и на 1 CPU тянет десятки комнат.
- **Хранилище** — один append-only JSONL-файл на комнату. На сервере живут только
  текст и метаданные сообщений: **тела медиа не хранятся вообще**. Медиа уходит
  участникам в реальном времени и кешируется в браузере (IndexedDB).
  Действует жёсткий бюджет комнаты с авто-прунингом.
- **Локализация** — русский и английский. Язык определяется по браузеру и
  переключается вручную на экране входа (выбор запоминается в `localStorage`).
- **AI-native** — упомяни `@ai` (или начни с `/ai`) в любом сообщении, и ассистент
  ответит всем участникам комнаты. Токены стримятся в реальном времени.
- **Превью ссылок** — сервер тянет Open Graph только для доменов из белого списка
  (это же защита от SSRF).
- **Markdown в сообщениях** — `**жирный**`, `*курсив*`, `` `код` ``, блок кода,
  `~~зачёркнутый~~`, ссылки `[текст](https://…)`, списки `-` и `1.`, цитаты `>`.
  Разметка собирается в DOM-узлы, а не в `innerHTML`, поэтому HTML из сообщения
  физически не может исполниться: экранировать нечего и библиотеки не нужны.
- **Одно имя на всю историю.** Имя — это подпись под сообщением (в `localStorage`),
  но подпись ровно одна: смена имени кнопкой ✎ в топбаре переписывает и прошлые
  сообщения. Сервер правит журнал комнаты (`POST /api/rooms/:id/rename`), поэтому
  разослать сообщения от разных имён и «притвориться двумя людьми» нельзя.
- **Стак сообщений.** Подряд идущие сообщения одного человека (пауза < 5 минут)
  рисуются одной группой: аватар, имя и время — только у верхнего. Лента не
  повторяет одну и ту же подпись на каждом пузыре.
- **Пузыри «по размеру».** И чужие, и свои сообщения занимают ровно столько,
  сколько в них текста: широкая «простыня» только у чужих убрана, лента больше
  не перекошена.
- **Свои сообщения выглядят как чужие** — с аватаром и временем, просто зеркально
  (подпись справа, над пузырём).
- **Никаких выдуманных «квадратиков».** В списке чатов вместо сгенерированного
  аватара комнаты — реальный состав: имена тех, кто в ней писал.

### Темы

Тема = набор CSS-переменных на `<body data-theme="...">`. Всё остальное общее,
поэтому новая тема — это ~7 строк CSS. Каждая тема обязана задать `--accent-ink`
и `--accent2-ink`, иначе текст на кнопке пропадёт на hover.

| # | ID | Характер |
|---|---|---|
| 0 | `matrix` | ядерная матрица: чистый люминофор `#00ff41` по абсолютно чёрному (по умолчанию) |
| 1 | `fuxxtylle` | прожаренная коричневая: медь и обугленное дерево, ни одного жёлтого |
| 2 | `mind-ctrl` | мрачная промывка мозгов: почти чёрный ультрамарин, вигнетка (центр — свет, края — чернота), единственный свет — холодный циан `#00e5ff`. Поверх фона вращается гипно-диск: яркий луч, за ним решётка секторов и кольца туннеля — 17 с на оборот, дыхание масштабом `.78→2.4` и глубокий пульс яркости. Диск под круглой маской (`mask-image`) и растворяется до края слоя: прямоугольник слоя в кадр не заезжает ни одним углом |
| 3 | `t-800` | эндоскелет: воронёная сталь и хром; красный `#e01010` — только highlight: непрочитанные в списке чатов и две кнопки-действия, «пригласить» и «отправить» |
| 4 | `darkness` | хардкор, абсолютный чёрный, только серый |
| 5 | `corporate` | IDE 90-х по палитре VGA/Turbo Vision: синий «рабочий стол» `#0000a8`, циановые рамки окон, белый текст, жёлтая подсветка `#ffff55`, серые диалоговые кнопки `#a8a8a8` |
| 6 | `angel` | светлая и мягкая: белый, светло-серые кнопки и графитовый текст — ни одного чёрного |
| 7 | `max` | официальная палитра max.ru (`#00bfff` / `#007aff` / `#6e1aff` / `#9500ff` / `#0d001a`) |
| 8 | `tg` | точные цвета Telegram |
| 9 | `vaporwave` | мечтательное ретро: сумеречный аметист и розово-голубой закатный градиент в логотипе |

вращается через независимые `rotate`/`scale` — это композитинг на GPU, без
перерисовки пикселей; слой живёт на `z-index:-1`, то есть под всем интерфейсом.

## Стили (второй параметр визуала)

Тема отвечает за **цвета**, стиль — за **материал**: геометрию, типографику и
приёмы оформления. Параметр живёт на `<body data-style="...">` рядом с темой,
поэтому любые сочетания работают: `matrix` + `skeuo`, `angel` + `brutal` и так далее.

| # | ID | Характер |
|---|---|---|
| 0 | `flat` | база (по умолчанию): плоский минимализм плюс хроматическая аберрация в заголовках — только `text-shadow`, ни слоёв, ни анимаций |
| 1 | `brutal` | так выглядел HTML в первый год своего существования: Times, квадратные углы, толстые рамки, жёсткие тени без blur, кегль крупнее общего (Times по x-height мельче моноширинного) — и вторичный текст тоже: подписи, мета и участники не мельчают. Цвета переключаются **рывком** — ни одного `transition` и ни одной анимации |
| 2 | `skeuo` | скевоморфизм 90-х: выпуклые бевелы (`border-style:outset`), градиенты, утопленные поля, «нажатые» кнопки, Tahoma. Строки чатов — обычные кнопки: на hover они заливаются акцентом и «вдавливаются», как все остальные |
| 3 | `julesverne` | латунная машина капитана Немо: ни одного прямого угла, всё выпуклое (фаски из `inset`-теней), шлифованный металл, гравёрные подписи, а на hover по кнопке пробегает отблеск вместо смены цвета. Клёпка — **редкий акцент, а не фон**: главные органы («создать чат», «пригласить», панель отправки, шапка чата и панель смены имени). Отблеска нет в списках — в «частоколе» переключателей тем/стилей/языков и в строках чатов: там он читался как мигание |

Правило: стили не должны грузить мобильные. Поэтому внутри только дешёвые приёмы:

- **Можно:** `border-style: outset/inset` (бевелы рисует сам браузер), статичные
  `linear-gradient` и `radial-gradient`, `background-image`-паттерны (клёпки),
  фаски из `inset`-теней, жёсткие тени (`5px 5px 0`) без blur,
  `text-shadow`, анимация `transform`/`opacity` на одном общем оверлее.
- **Нельзя:** `backdrop-filter: blur()` на каждом сообщении, `filter: hue-rotate()`
  в анимации, большие `box-shadow` с размытием на множестве элементов,
  анимация `background-position` по градиенту (перерисовка каждого кадра),
  `mix-blend-mode` на пузырях сообщений.
- Всё движение отключается системной настройкой `prefers-reduced-motion: reduce`.

## Локальные «Мои чаты», непрочитанные и аватары

- **Чаты не теряются.** Список чатов, в которые ты заходил, живёт в `localStorage`,
  а история сообщений — на сервере. Закрыл вкладку — вернулся позже и прочитал
  всё, что пришло: сервер ничего не выбрасывает (только авто-прунинг по бюджету).
- **Непрочитанные.** На экране входа у каждого чата показано число новых сообщений,
  а суммарное — в заголовке вкладки (`(3) Мессенджер`). Считает сервер:
  `GET /api/rooms/:id/unread?since=<время>&exclude=<clientId>` — экран входа не
  тянет историю целиком, только число. Пока вкладка открыта, список обновляется
  раз в 10 секунд, а при возврате во вкладку — сразу.
- **Аватары без хранения на сервере.** По умолчанию аватар вообще нигде не лежит:
  он генерируется на клиенте из идентификатора (цвет из хеша + буквы имени).
  Свою картинку можно поставить — она обрезается до 64×64 в браузере, лежит в
  `localStorage` и передаётся участникам комнаты через `POST /api/rooms/:id/avatar`
  **только в реальном времени**. Сервер валидирует (только `image/png|jpeg|webp`,
  до 48 КБ) и релеит событие, но никуда его не пишет: ни в журнал, ни в память.
  Кто подключился позже — получит картинку, когда её владелец о ней напомнит
  (это происходит само при входе нового участника) или останется со сгенерированной.
- **Онлайн — это люди, а не вкладки.** Присутствие считается по уникальным
  `clientId`, поэтому несколько вкладок одного человека показываются как один онлайн.

Чего пока нет (осознанно отложено): пуш-уведомления при полностью закрытой вкладке
(для этого нужен Web Push + service worker + VAPID-инфраструктура на сервере).
Сейчас уведомления приходят, пока вкладка открыта, а непрочитанные видны в
заголовке и в списке чатов.

## Безопасность и анти-абьюз

- Аккаунтов нет → нечего угонять. Доступ = неугадываемый `roomId` (~72 бита).
- `Content-Security-Policy`, `X-Frame-Options: DENY`, `nosniff`, `no-referrer`.
- Все ограничения по размеру и частоте: сообщение, вложение, IP, ИИ.
- Валидация медиа: только `image/*` и `video/*`, лимит размера.
- Рендер только через `textContent` → XSS через сообщения невозможен.
- Ключ ИИ никогда не покидает сервер; клиент общается только с ним.
- Превью только для доменов из белого списка (анти-SSRF).

Хранение: **файлы на сервере не хранятся вообще.**

- Текст и метаданные сообщений — в журнале комнаты, переживают перезапуск сервера.
- Медиа передаётся участникам в реальном времени и кешируется в браузере (IndexedDB),
  поэтому на своём устройстве ты видишь его и после перезагрузки страницы.
- Кто подключился позже, медиа уже не получит: вместо картинки он увидит пометку
  «это изображение не хранится на сервере — попросите отправителя прислать его
  заново» — и отправитель может просто переслать файл.
- Аватары не хранятся вообще: либо генерируются в браузере из идентификатора
  человека, либо передаются живым участникам комнаты и остаются только у них
  (в `localStorage` и в памяти вкладки).

## Деплой (VPS 1 CPU / 2 GB RAM)

Zero-infrastructure: нужен только Node.js. Статика и API отдаёт один процесс.

Юнит сервиса версионирован вместе с кодом — `deploy/messenger.service`. CI рендерит из
него `/etc/systemd/system/<SERVICE_NAME>.service` и ставит **идемпотентно**: если
содержимое совпало, файл на VPS не трогается вообще (ни записи, ни `daemon-reload`).
Так «как настроен сервис» видно в истории git, а не только руками на сервере.
Заглушки шаблона: `__DEPLOY_PATH__`, `__SERVICE_NAME__`, `__SERVICE_USER__`, `__NODE_BIN__`.

Секреты устроены так же: `.env.example` — шаблон, из которого CI рендерит
`/opt/messenger/.env` (заглушки `__AI_API_KEY__`, `__AI_BASE_URL__`, `__AI_MODEL__`
подставляются из секретов GitHub). Ручного шага «зайти на сервер и завести `.env`» в
деплое нет: файл нужен юниту (`EnvironmentFile=`), и его отсутствие — гарантированная
поломка на старте, а не мелочь.

Развёрнутый вид (значения по умолчанию — те же, что в шаблоне):

```ini
[Unit]
Description=Messenger — HTML-native мессенджер
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
WorkingDirectory=/opt/messenger
EnvironmentFile=/opt/messenger/.env
ExecStart=/usr/bin/node server/index.js
User=www-data
Restart=always
RestartSec=2
StandardOutput=journal
StandardError=journal

[Install]
WantedBy=multi-user.target
```

### Автодеплой: `.github/workflows/deploy.yml`

Пуш в `master` → проверка синтаксиса (`node --check` по всем JS + баланс скобок в
CSS) → проверка секретов и приватного ключа → `rsync` проекта на VPS → проверка и
(при расхождении) установка systemd-юнита → рендер `.env` из секретов (идемпотентно) →
подготовка `data/` под сервисного пользователя → `systemctl restart` → health-check
`/api/health`.
Если сервис не поднялся, джоб падает, показывает `systemctl status` и печатает последние
строки `journalctl`.

Что нужно один раз завести в репозитории (Settings → Secrets and variables → Actions):

| Секрет | Обязательный | Пример | Смысл |
|---|---|---|---|
| `SSH_HOST` | да | `203.0.113.10` | адрес VPS |
| `SSH_USER` | да | `deploy` | пользователь с правом `sudo systemctl restart messenger` |
| `SSH_KEY` | да | `-----BEGIN OPENSSH PRIVATE KEY-----…` | приватный ключ **без пассфразы**; публичную часть — в `~/.ssh/authorized_keys` на VPS |
| `DEPLOY_PATH` | да | `/opt/messenger` | куда раскладывать проект |
| `SERVICE_NAME` | нет | `messenger` | имя systemd-юнита (по умолчанию `messenger`) |
| `APP_PORT` | нет | `8787` | порт для health-check (по умолчанию `8787`) |
| `SSH_PORT` | нет | `22` | порт SSH |
| `SERVICE_USER` | нет | `www-data` | от кого крутится сервис (`User=` в юните) |
| `NODE_BIN` | нет | `/usr/bin/node` | путь к node для `ExecStart` — нужен, если node из nvm/asdf, а не из `/usr/bin` |
| `MANAGE_UNIT` | нет | `true` | `false` — не трогать юнит на VPS (ставить руками) |
| `AI_API_KEY` | нет | `sk-…` | ключ провайдера ИИ: CI кладёт его в `.env` на VPS, клиенту он не уходит. Без него сервис поднимется, но ИИ ответит «не настроен» — деплой даст предупреждение |
| `AI_BASE_URL` | нет | `https://api.deepseek.com/v1` | OpenAI-совместимый провайдер (нет секрета — значение из шаблона) |
| `AI_MODEL` | нет | `deepseek-chat` | модель (нет секрета — значение из шаблона) |
| `MANAGE_ENV` | нет | `true` | `false` — не трогать `.env` на VPS (заводить руками) |

Детали, которые важны:

- `rsync` идёт с `--delete`, но с `--exclude .env` и `--exclude data/`, поэтому
  секреты и журналы комнат на VPS **не затираются** никогда.
- Сборки нет: проект без зависимостей, деплой — это копирование файлов + рестарт.
- На VPS нужны только `rsync`, `node >= 18` и `sudo` без пароля у деплой-пользователя:
  ни `git clone`, ни `.env`, ни юнит, ни каталог данных руками заводить не нужно.
  «Новый сервер за ноль шагов»: один пуш (или кнопка Run workflow) раскладывает код,
  рендерит `.env`, ставит юнит, готовит `data/` и поднимает сервис.
- Юнит ставится идемпотентно: CI рендерит `deploy/messenger.service`, сперва кладёт
  результат в `/tmp` на VPS и проверяет `systemd-analyze verify` (ловит и синтаксис, и
  несуществующий `ExecStart`), и только если содержимое отличается от живого файла —
  пишет его (`install -m 0644`), делает `daemon-reload` и `enable`. Совпало — шаг не
  делает ничего; зато сломанная правка юнита в PR не гасит сервис (проверка идёт до
  записи). Заменённая версия остаётся в `/tmp/<имя>.service.bak`.
- Почему это в деплое, а не руками на сервере: юнит — такой же код сервиса (путь,
  пользователь, порт), и, живя в единственном экземпляре на VPS, он дрейфует. Плюсы:
  одна правда в git, правки ревьюятся, смена пути/пользователя не забывается. Минусы:
  деплой становится ещё и «инфраструктурным» (сломанный юнит мог бы погасить сервис —
  отсюда проверка до записи и health-check), а деплой-пользователю нужен root. На
  одиночном VPS это оправдано; хочешь строже — выдай `sudo` не на пачку команд, а на
  один скрипт-обёртку, который сам валидирует юнит. Права нужны на: запись в
  `/etc/systemd/system/`, `systemctl daemon-reload`, `systemctl enable/restart/is-active`,
  `journalctl`, запись `.env` и создание/`chown` каталога `data/` в `DEPLOY_PATH`.
  Помни: право писать юнит = возможность запустить от root что угодно, поэтому
  `NOPASSWD` выдавай отдельному деплой-пользователю, а не общему.
- Владелец файлов: деплой идёт от `SSH_USER`, код ложится его владельцем, а сервис по
  умолчанию работает от `www-data` — поэтому `data/` CI создаёт и `chown`-ит под
  `SERVICE_USER` сам (иначе приложение падает с `EACCES` на старте: `server/config.js`
  первым делом делает `mkdir data/rooms`). Живой `.env` при этом лежит `0600 root:root`:
  systemd читает его до сброса прав, а процессу сервиса он не нужен.
- `.env` на VPS — **не место для правок руками**: следующий деплой перезапишет файл
  (если содержимое не изменилось, не трогается вообще, и рестарта тоже не будет).
  Прежняя версия перед заменой остаётся в `/tmp/.env.bak`. Единственная правда — секреты
  GitHub (`AI_API_KEY`, `AI_BASE_URL`, `AI_MODEL`): добавил секрет, перезапустил деплой,
  ключ на месте. Хочешь ручное управление обратно — `MANAGE_ENV=false`.
- `MANAGE_ENV=false` — аварийный выход: CI вообще не касается `.env`, и тогда его надо
  заводить на сервере самому (`install -m 0600 -o root -g root`), иначе юнит с
  `EnvironmentFile=` не запустится.
- Ручной запуск тоже есть: `workflow_dispatch` (кнопка Run workflow в Actions),
  а параллельные деплои блокируются через `concurrency`.
- Секреты проверяются первым шагом джоба. Раньше их отсутствие выглядело как
  загадочное `usage: ssh …` и код 255: GitHub **не** падает на несуществующий
  секрет, а молча подставляет пустую строку — адрес назначения собирался в
  `"@"`, ssh получал пустой хост и печатал справку. Теперь прогон падает сразу
  и говорит «Не заданы: …». Там же ловится ключ не в формате OpenSSH (`.ppk`,
  с пассфразой, обрезанный) и CRLF из Windows-копипасты. Адрес, порт и ключ
  описаны один раз в `~/.ssh/config` (`Host vps`), поэтому больше не
  дублируются в пяти командах.

Nginx (важно: SSE требует выключенного буферизования):

```nginx
location / {
  proxy_pass http://127.0.0.1:8787;
  proxy_http_version 1.1;
  proxy_set_header Connection "";
  proxy_buffering off;          # обязательное условие для SSE
  proxy_read_timeout 3600s;
}
```
